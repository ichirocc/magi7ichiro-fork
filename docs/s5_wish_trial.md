1. **試算の中身**＝「同じ盤面で確実に消える分（確定）」＋「違反起点修復（`ViolationComponentRepair`、以下 VCR）で減る分（見込み）」。
   見込みは**希望を残したまま同じ修復を回した値（対照）を差し引いた分**だけを出す。VCR は既定の Params・候補プールは空・時計を使わない＝決定的。
2. **机上評価（§13、3 回・164 行）**: VCR が「減る」と出した行は v2 35/36・v3 39/40 で本当に減った（過大は両方とも同じ 1 行）。

3. **確定操作**＝「希望 1 件の取り消し＋本実行」を **元に戻す 1 回**で希望と勤務表がまとめて戻る専用操作。試算の盤面は採らない（ユーザー決定）。

6. 範囲と入口は利用者が決めた（2026-09-24、§14）: **人手不足の日の希望も最初から含める（S5a と S5b を一度に）**・c3w は前日の希望も並べる・
   「希望とルールがぶつかっています」の分岐を関わる希望全般へ広げる・確定を元に戻したら「下限の見込み」の入口も戻す。

## 1. 目的と非目的
- 目的: 必須違反に希望が関わる盤面で、**どの 1 件を取り消せば必須違反が減るか**を、取り消す前に比べられるようにする。
- 非目的（決定済み・再提案しない）:
  - どの希望を取り消すかを自動で選ばない・自動で確定しない（3.492.0・3.401.0、`docs/automation.md`「希望固定…自動変更しない」）。
  - 複数件の同時取り消し・見込みの合計は出さない（代替関係があり足せない＝§13 c07）。
  - SOFT（要調整）の見込みは出さない（apt の実効目標は希望数から作る＝希望 1 件で目標自体が動き、比べられない）。
  - 試算の盤面を採用しない（ユーザー決定「仮盤禁止」）。
  - 配置固定の再評価（同じ盤面で数え直すだけ）を主結果にしない（ユーザー決定。§13 で全行 0＝裏付け）。

## 3. 何を数えるか
記号: いまの state＝st、盤面＝B、希望 (i,j)=k を消した state＝st2、clear＝`HardRepairCore.clearCappedCells`（本実行の入口と同じ）。

| 記号 | 定義 | 意味 |
|---|---|---|
| H0 | check(st, B).hard | いま表示中の必須違反 |
| Hx | check(st2, B).hard | 同じ盤面で希望だけ消した値 |
| a | H0 − Hx | 同じ盤面で消える分（pref と c3w、1 件で最大 2） |
| Rk | VCR(st, clear(st,B)).hard | 対照（希望を残したまま修復） |
| Rr | VCR(st2, clear(st2,B)).hard | 希望を消して修復 |
| P_keep | min(H0, Rk) | 希望を残してもう一度つくった場合の予測 |
| P_cancel | min(Hx, Rr) | 取り消してもう一度つくった場合の予測 |
| att | P_keep − P_cancel | 取り消しに帰属する減少（負もありうる） |
| a' | min(a, max(0, att)) | 帰属する確定分 |
| b | max(0, att − a) | 確定を超える見込み |

- att < a は Rk < H0 のときだけ起きる（Rk ≥ H0 なら att ≥ a）。例: c3w は前日側のセルに印が付き、VCR は希望固定のセルしか拒まないので、
  希望を残したままでも前日セルを動かして同じ c3w を消せる＝対照が a をすでに含む。VCR は評価回数・起点を 1 回の呼び出しで共有して
  最初の改善を採るので、Rr > Rk（att が負）もありうる。
- **保証（コードで確認）**: `runV6FullOptimize` の keep-best の基準は `check(st0, sched0)`＝確定操作では check(st2, B)＝Hx。
  `betterReport` は必須が先なので、本実行の結果の必須は ≤ Hx。停止は盤面を sched0 に戻す＝Hx。失敗は state も盤面も変えない＝Hx。
  → 「取り消せば、結果は必ず必須 Hx 件以下」は言える。見込み（P_cancel）は言えない。
- 族の内訳は出さない（VCR は族の入れ替えを禁じない＝内訳の意味がエンジンに依存する）。必須の件数だけ。

## 6. 確定操作「希望を取り消して、もう一度つくる」
既存の `removeWish`（`applyStructure`＝Undo「設定の変更」＋refreshCheck）→`runV6FullOptimize`（Undo「勤務表の作成」）をつなぐと
Undo が 2 段になり、1 回目の Undo は「希望なし＋元の盤面」という中途半端な組に戻る。専用の操作にする。画面はダイアログを閉じてから呼ぶ。

1. `st=state`, `b=currentSchedule`（null なら何もしない）
2. `runBlockedByInFlight("希望の取り消し")` なら終わり
3. 照合: `st === token.state && boardKey(b) == token.boardKey && st.wishes["i,j"] == token.shift`。違えば「勤務表か希望が変わりました。
   もう一度試算してください。」で終わり（何も変えない。試算結果は消さない）
4. 試算ジョブを取り消す
5. `ns = st.copy(wishes = st.wishes - "i,j")`。`ensureValidForRun(ns, b)` が偽なら終わり（何も変えない）
6. `pushUndo("希望の取り消しと、もう一度つくる")`（**希望が残っている state と B を 1 回だけ積む**）
7. `state = ns`。`++checkSeq; checkJob?.cancel()`（走っている検査が取り消し前の希望を画面へ書き戻さないように）。
   `_ui.update { wishes = ns.wishes, structureEdited = true, editRev + 1, runSummary = null }`
   （applyStructure は使わない＝2 回目の push と refreshCheck を起こさない。`ui.wishes` を書くのは makeUi だけなので、ここで直に揃える）
8. **`saveNow()`**（同期・原子・世代ゲート付き）。本実行が書く実行マーカーより先に（なし, B）をディスクへ置く
   （`autoSave()` は 1.2 秒後の予約なので、その間の異常終了で「入力は自動保存済み」の案内と中身が食い違う）
9. `logOp("I", "希望取消＋もう一度つくる: 名前 N日（記号） H0/Hx/Rk/Rr/P_cancel")`

## 8. 鮮度・並行・取消
- 試算の文脈 `ctx = (state の参照, boardKey(currentSchedule))`。結果と対照 Rk は VM 側に ctx つきで持ち、UiState には完了の合図（`wishTrialRev`）と
  試算中の行だけを出す。画面は `vm.wishTrialFor(i, j, k)` で読み、VM は**読むたびに ctx を照合**してずれていれば「古い」を返す
  （`GuidedFixDialog` の `shortageFixCandidates` と同じ「画面が問い合わせる」形）。盤面を書き換える 24 か所に消去を足さなくても、古い結果は出ない。
- **保持の規則**: 結果と対照は、**別の ctx で新しい試算を始めたときにだけ**入れ替える（1 世代）。読む・照合する・確定する、では消さない。
  → 確定を元に戻すと state は試算時と**同じ参照**、盤面も同じ内容に戻る（UndoSnap は state の参照と盤面の複製を持つ）＝他の行の結果がそのまま有効。
  ただし確定から元に戻すまでの間に別の ctx で試算を始めれば戻らない。
- ジョブ: `wishTrialJob`（viewModelScope・Dispatchers.Default）。通し番号 `wishTrialSeq` で世代を管理（cancel は非同期＝`fixSeq` と同じ理由）。
  完了時（main）に seq と ctx を照合し、ずれていれば捨てる。
- **取り消す場所**（ジョブの取消だけ＝CPU を返す。結果は消さない。正しさは照合が守る）: `stop()`・`beginBoardJob()`（前景の盤面ジョブの入口）・
  `runInBackground()`（beginBoardJob を通らない）・確定（§6 の 4）・ダイアログの `DisposableEffect` の `onDispose`（閉じる・行を押してセルへ移る・
  Activity の作り直し、どの閉じ方でも 1 か所。行を押す経路は onDismiss を通らない）。
- 1手の探索（fixJob、止められない）と同時に走っても正しさは変わらない（どちらも読むだけ）。ProblemCache（1 件だけの global）を取り合って遅くなるだけ。

## 10. 停止・失敗・プロセス終了
- 停止: 盤面は B、希望は消えたまま（Hx）。既存文に「（希望の取り消しはそのままです。元に戻すで希望も戻ります）」を足す。

  pushReport、文言「勤務表の作成は終わりましたが、最後の処理でエラーが起きました（種類）。表示は今の勤務表です。」（S5 は同じ接尾辞）。
- プロセス終了: 取り消しは本実行の前に同期保存する（§6 の 8）ので、再起動で出るのは（なし, B）か（なし, 結果）。Undo の履歴も**操作ログもメモリ上**

- **E. 入口を広げる**: WISH 分岐の条件を「関わる希望がある」（S5a・S5b の行が 1 件以上）へ。c3n にだけ掛かる希望も「下限の見込み」（50 秒改善なし）を
  待たずに開ける。
- **D. 元に戻したら「下限の見込み」の入口も戻す**: 確定を元に戻して state の参照と盤面キーが確定前と一致したら `stalledHardFamilies` を確定前の値に戻す
  （VM が確定時に (state の参照, 盤面キー, 値) を控える。Kotlin・C# 同じ）。E で WISH 分岐が広がるので、効くのは見出しを「下限の見込み」に保つことだけ。
- 机上で決めたもの: C「0 の行に確定ボタンを出さない」は**出す**（0 の行の 10/18・8/14 は本当は減った）。

## 15. 検証で退けた指摘
- 背景実行が runInBackground を通らずに始まり試算と並走する: WorkManager の再開は実行マーカーが消えていて running を立てない。プロセス復元では
  ホームが実行中の表示になりダイアログに入れない。
- 回転でダイアログが消えると試算が止まらない（上限が無い）: VCR は回数で上限があり、結果は ctx つきで残るだけ（取消は §8 の onDispose に寄せた）。
- 中断の案内で取り消した希望を名指しすべき: すべての編集に共通する性質（Undo はメモリ上）で、ディスクの組は I7 のとおり。任意の改善として backlog。
- 両言語の VCR は既定の経路で同値（後発の Params はすべて既定 OFF）。共有 fixture のテストは補強として T8 に入れた。
  なお C# の `NormalizeSchedule` が欠損セルを 0 で埋めていた（Kotlin は 3.475.0 から -1）のは S5 と別の C# のずれで、同日に直した。
